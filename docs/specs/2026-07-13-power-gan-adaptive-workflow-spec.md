# power-gan 渐进承诺与自适应交付工作流规格说明

> 2026-07-26 修订：Issue [#34](https://github.com/zhan7653/ohmypowers/issues/34) 在保持本规格自适应边界的基础上，加入已由当前 Codex 运行时验证的轻量模型路由和独立 reviewer 执行规则，并取代 Issue #25 中要求双轨模式确认和 Agent Dispatch Plan 的路由决定。

## 背景

当前 Loop Engineering 流程已经通过风险分级、减少实施 Agent、延后最终评审、限制等待轮询、减少重复验证以及允许简单 Issue 直接执行等方式降低了执行成本，但 [Issue #29](https://github.com/zhan7653/ohmypowers/issues/29) 及 [PR #30](https://github.com/zhan7653/ohmypowers/pull/30) 暴露了更早发生的根因：模型在需求对齐之后，自行补充了大量实施方案、安全保证和验证义务，再通过一次没有明确指向这些高成本边界的确认把它们升级成用户合同。

Issue #29 的原始需求主要是：

- 日报生成过程中允许用户补充个人想法；
- 识别可以提炼为 Skill 或自动化的重复内容；
- 提出可以沉淀为全局或项目指令记忆的建议，并在用户确认后影响 Codex。

最终 Task Contract 扩展为 20 条验收标准，并进一步加入受管理区块、准确 diff、漂移、冲突、权限、大小限制、审计、修订和删除等要求。后续 Execution Blueprint 和 Dispatch Plan 又冻结了路径、接口、任务拆分、验证矩阵和 reviewer 拓扑。用户形式上确认了完整内容，但大量高成本决定实际由模型提出，没有经过逐项的价值、成本和风险辩论。

PR #30 最终新增 3,815 行，其中 1,889 行为测试；首版实现之后又经历多轮证据、审计、并发、恢复和验证加固。后续 [PR #31](https://github.com/zhan7653/ohmypowers/pull/31)–[PR #33](https://github.com/zhan7653/ohmypowers/pull/33) 及本地重构降低了执行与评审成本，但没有完全解决以下问题：

- 用户拥有的产品决定与模型拥有的实施决定没有清晰分离；
- 模型工作假设可能被写成规范性合同；
- 当确认对象本身没有被清楚复述时，简短回复可能被错误解释为接受多个材料决定；
- 实施前的 Blueprint 和测试设想会限制实施中的调整空间；
- 模型倾向于提供一个推荐答案并寻求确认，而不是坚持有证据的异议；
- 为每个任务生成持久 Markdown 会造成文档膨胀、无人阅读和代码与文档漂移。

本规格重新设计从需求对齐到完成验证的核心编码工作流，不要求兼容现有 `power-think`、`power-grill`、`power-loop`、`power-verifier` 的阶段、格式或产物。

## 目标

建立一个以渐进承诺为核心的工作流：

- 用户决定外部结果、范围、材料成本和风险取舍；
- 模型决定可逆的内部实现方式，并可在实施中持续调整；
- 只有仍未解决或新引入的材料决定需要用户确认，持久化则取决于任务和仓库是否需要长期记录；
- 模型必须提出有证据的反对意见，但不能为了表现独立而仪式性抬杠；
- 验证策略根据最终实现和实际风险决定，不由早期方案冻结；
- 简单任务可以低摩擦直接完成，复杂任务可以在同一工作流中进入 Deep Grill；
- 重要决定通过 Issue、PR 和 commit 形成可追溯链路，不自动生成仓库决策 Markdown；
- 独立检查按风险追加，并且不能伪造上下文独立性。

## 核心原则

1. **用户拥有 what/why，模型拥有可逆的 how。**
2. **只冻结已经明确承诺的材料决定。**
3. **实施方案是工作假设，不是用户合同。**
4. **持久化决定，不持久化完整工作过程。**
5. **代码、测试、schema、类型和配置表达当前事实，Issue 保存为什么这样决定。**
6. **模型有义务反对，但普通技术偏好不构成无限 veto。**
7. **验证依据来自最终实现，不来自早期猜测。**
8. **流程复杂度必须与任务风险和交付价值相称。**

## 需求

### 功能需求

#### FR-1：主工作 Skill

提供一个名为 `$power-gan` 的主工作 skill，统一承载需求对齐、Deep Grill、自适应实施和相称的自验证。

操作性指令必须以 `Goal`、`Success`、`Constraints`、`Decision Rules`、`Validation` 和 `Stop Rules` 为六个主结构，使目标、完成口径、约束、判断规则、验证和停止条件成为主协议，同时保留 Grill Me 作为材料对齐的核心行为。

`$power-gan` 必须区分两个工作目标，但这些名称是可选简写，不是 Agent 要求用户选择的菜单：

- `ALIGN_ONLY`：只对齐决定，不实施；允许只读调查仓库和托管上下文，输出当前决定或持久化建议后停止。
- `DELIVER`：完成必要对齐后实施，并根据最终实现进行自验证。

当用户意图不明确时，只询问是否需要实施，不得默认选择 `DELIVER`。用户直接要求实现时，该请求已经授权其明确范围内的可逆源代码修改。

从 `ALIGN_ONLY` 切换到 `DELIVER` 必须有用户明确授权。`DELIVER` 实施中可以重新进入对齐状态处理材料偏移，但不得因此创建新的 skill handoff。

#### FR-2：对齐深度

`$power-gan` 必须在同一工作流中支持两种对齐深度，但只在用户主动使用这些名称时将其视为简写：

- `FAST`：只解决阻塞当前工作或改变材料边界的决定；
- `DEEP`：使用 Deep Grill 沿材料决策树逐项建立共同理解。

用户可以从一开始明确要求 Deep Grill。Agent 发现多个相互依赖的材料决定或高风险边界时，应直接沿实际决策树追问；只有更深的访谈会显著扩大用户预期的时间或范围时，才需要先解释原因并确认是否继续。

#### FR-3：Deep Grill 行为

Deep Grill 必须：

- 首轮和后续每一轮都围绕当前最高杠杆的材料分支或决策层：用一个短段落陈述回答该批问题所需的事实与判断，不使用项目符号列表；提出一至三个最高杠杆问题，为每个问题给出推荐及理由，然后停下来等待；
- 当前问题复杂、高风险，或后续问题依赖前一个答案时只问一个；只有问题处于同一决策层、彼此独立且可以一起回答而不隐藏材料选择时，才合并为两个或三个；
- 允许用编号列出问题，但不得把编号问题变成编号备选方案、A/B/C 菜单或固定检查表；
- 从当前共同理解中选择杠杆最高的未决问题批次，让用户的回答决定下一条分支；
- 对每个真实问题给出推荐答案和证据，而不是只把选择抛回用户；
- 每次回答后更新当前理解，并在必要时调查新出现的仓库事实；
- 不播报访谈阶段、模式切换或未来问题序列；
- 不在提问前倾倒“设计基线”或完整方案，不提前替用户解决下游材料决定，也不把多个决定藏进一个推荐；
- 将此前涉及用户材料边界的推荐、提案、假设或草稿视为未决，直到用户明确接受；已验证的仓库事实直接作为事实，Agent 自有的可逆实现假设不进入用户确认循环；“先设计”只授权进入访谈，不代表授权 Agent 代写完整设计；
- 仓库推导的假设只能作为非材料、可逆实现的可见工作默认值，不能因为用户没有反对就解决用户拥有的材料边界；
- 上一轮存在尚未确认的推荐时，下一批问题必须继续包含该推荐，且不得加入依赖它的下游问题；独立的同层问题仍可在一至三个问题的上限内合并；
- 用户只回答一部分问题时，已回答问题按正常确认规则处理，未回答问题继续保持未决，不得把沉默解释为接受；
- grill 回合不输出设计草案、验收标准、多项决策列表或编号备选方案，只针对当前每个问题给一个推荐；用户拒绝或主动询问替代方案后，下一轮再探索其他路径；
- 优先解决可观察的产品与状态语义，再讨论接口语法或兼容机制，除非接口本身就是未决产品合同；
- 先解决上游决定，再进入依赖它的下游分支；
- 对可以通过仓库、代码、Issue、PR 或文档查明的事实自行调查；
- 只追问属于用户权责的外部结果、范围、成本、风险、授权和停止条件；
- 用户拒绝推荐或主动询问替代方案时，下一轮再探索一条可信路径，不把候选方向一次性做成菜单；
- 保持自然的技术对话，让每个问题都像技术搭档真正会问的问题，不把追问变成检查表、决策备忘录、审批关卡或重复的选项菜单；
- 对未解决边界坚持追问，而不是为了填满字段继续提问；
- 允许新证据推翻旧前提并回到相关分支；
- 在没有未解决材料分支时结束，而不是穷举所有可能的实施细节。

每轮对齐都维护一个紧凑的 Decision Ledger，固定使用“已确认”“待定”“默认（可改）”“已委托”四类，仅记录材料项。未确认的推荐在用户接受、拒绝或修改前始终留在“待定”；部分回答不能让未回答项自动确认。“剩下的你定”等明确委托只覆盖当前已命名的待定项，不覆盖安全、合法性、不可逆操作、外部支出或缺失授权。Ledger 是会话运行状态，不作为 Blueprint 或问题清单持久化；需要 Decision Record 时，由“已确认”和“已委托”内容生成。

#### FR-4：推荐与有据异议协议

对于材料决定，Agent 必须：

1. 从当前证据出发给出自己的判断和推荐；
2. 优先询问用户拥有的结果或边界，不把可逆接口和实施细节升级给用户选择；
3. 不以 A/B/C 或其他菜单形式一次性抛出候选方向；用户拒绝当前推荐或询问替代方案后，下一轮再探索一条可信路径；
4. 只在证据显示真实矛盾、成本、风险或被忽略后果时提出异议，并在相关推理中直接说明；
5. 只在实际材料边界仍未解决时要求用户确认或修正，让回答自然决定后续问题。

Agent 必须保持独立判断，不得奉承、迎合或镜像用户立场，也不得把用户偏好、信心、身份或期望结论当作证据。可信反证出现时必须清楚指出并解释后果；没有反证时不得为了唱反调制造异议。

当模型有具体证据认为用户方案过度复杂、逻辑矛盾、成本显著高于收益或忽略重要风险时，必须明确提出异议和替代方案。

如果用户第一次坚持但没有回应关键异议，模型必须再次指出仍未解决的问题。用户明确理解并接受代价后，拥有普通产品决定的最终权力。

安全、权限、违法、不可满足的事实矛盾、不可验证的完成声明或不可逆授权不足仍然构成停止条件。

没有可信异议时，模型不得为了表现独立而虚构反对意见，也不得在每项推荐后仪式化追加反方观点。

#### FR-5：材料决定与有效确认

材料决定按以下四项测试：

- M1（可观察行为）：改变用户或外部系统依赖的行为或数据；
- M2（公共契约）：创建或改变 API、schema、存储格式、配置面、CLI、wire protocol，或跨模块、跨团队共享的契约；
- M3（长期成本或风险）：采用长期生产依赖，建立运行、部署、存储或数据所有权边界，或承诺支出、配额、安全和权限边界；
- M4（反转代价高）：涉及数据迁移、已发布版本、外部承诺或落地后昂贵的撤销操作。

公共或私有不是唯一划分依据。局部函数签名、私有 helper 和容易替换的抽象仍由 Agent 自主决定，不能仅因为被称为“架构”就升级为材料决定。

确认是否有效取决于上下文是否能够唯一识别被确认的边界，而不是回复使用了“可以”“确认”还是其他短语。当前一条问题已经清楚复述完整范围并明确询问是否整体接受时，简短确认有效；只有存在多个合理指向时才追问。

#### FR-6：自适应实施

完成只读调查和材料决定对齐后、首次修改源代码前，Agent 必须让用户看见完成口径、硬约束、当前最小可信路径、验证方向和真实暂停条件。前置调查在证据足以说明这些边界时结束，不得在启动前推导完整设计或验证矩阵；不得把尚未对齐的材料架构或共享接口选择藏在“当前路径”中。

用户直接要求实现时，该请求已经是明确范围内的启动授权。只有当前执行边界引入新的未决材料承诺、用户明确要求先审设计再编码，或缺少外部/不可逆授权时，Agent 才等待进一步确认。该授权不冻结 Blueprint、文件列表、内部接口、测试矩阵或每项实施细节。

Agent 可以维护简短、非规范性的 Working Strategy，用于当前实施的路径、顺序、接口假设和验证思路。

Working Strategy：

- 默认不持久化；
- 在已授权边界内调整不需要用户逐项确认；
- 可以随着仓库发现和实现结果调整；
- 不能成为最终验证合同；
- 不能向用户承诺固定文件、函数、命令、任务拆分或 reviewer 数量。

当内部调整不改变完成口径、硬约束、材料成本或风险边界时，Agent 应直接继续工作。重要的重新规划使用明确标注为“无需回复”的非阻塞进度通报；真正需要用户决定时必须明确说明执行已经暂停。

#### FR-7：材料偏移

实施中出现以下情况，而当前决定没有覆盖时，Agent 必须暂停并重新对齐：

- 与精简执行边界中的完成口径或硬约束冲突；
- 新的持久状态、权限、安全或隐私边界；
- 迁移、兼容性、并发或不可逆操作；
- 新增可以独立交付的功能；
- 影响系统或成本超出启动时诚实描述的边界；
- 实现或验证成本相对对齐阶段的合理理解显著膨胀；
- 无法可信地产生已承诺的验证证据；
- 原决定与仓库事实发生材料冲突。

“显著膨胀”是指继续实施将超出用户明确给出的预算或周期，或者 Agent 已无法诚实地沿用此前对任务规模、风险等级或交付边界的描述。不得仅用代码行数或测试数量机械判断。

重新对齐时只展示变化和影响，不重新 grill 整份历史决定。Agent 应推荐最小可信处理；只有多个方案确实可行时才列出替代路径，不得固定凑出缩减、拆分和继续投入三个选项。

#### FR-8：持久化载体

持久化采用最小充分载体：

- 高风险、长周期、跨会话或多人协作，且需要规范决策来源的任务优先使用 Issue；
- 普通 PR 级任务可以只在 PR 中记录结果、重要取舍和验证；
- 极小、局部且没有长期决定价值的修改可以只依赖 commit；
- 材料决定本身不自动授权托管写入，也不强制创建 Issue；
- 不自动生成仓库内的决策 Markdown 文档；
- 文档本身是交付物或用户明确要求维护少数架构文档时，不受此限制。

对齐结束时，Agent 必须主动选择并说明最小充分载体。需要新 Issue 且不存在规范来源时，主动给出 Decision Record 并请求托管写入授权，不等待用户先提出 Issue；没有持久化价值时可以明确选择不建立长期记录。

能够机器化表达的长期约束应优先进入测试、schema、类型、配置、静态规则或代码结构。只有需要指导未来 Agent 行为时，才经过明确确认写入就近的 `AGENTS.md`。

#### FR-9：Decision Record

需要 Issue 持久化时，Issue body 保存当前有效且精简的 `Decision Record`。在不与仓库模板冲突时，记录：

- `Decision status`；
- 仓库采用修订号时的 `Decision revision`；
- 目标和可观察结果；
- 范围和非目标；
- 已确认的材料决定；
- 每项决定的简短理由；
- 仅在有助于解释非直观边界或避免未来重复争论时，记录最接近但未选择的方案；不得为了填充格式而编造替代方案；
- 已接受的材料成本和风险；
- 暂停、停止和重新打开条件。

Decision Record 不得包含 Blueprint、完整实施计划、文件列表、内部接口、测试矩阵、Agent 分工、reviewer 拓扑或完整对话。

仓库使用 `Decision revision` 时，只有用户确认的材料决定变化才递增。评论、标签、关联 PR、措辞修正和普通生命周期变化不递增 revision。

#### FR-10：Decision Notes

Issue 创建后出现材料决定变化、关键授权、任务拆分、替代、暂停或完成时，可以使用简短 comment 保存 `Decision Note`。

Decision Note 可以记录：

- 发生变化的问题；
- 变化原因或新证据；
- 最终决定；
- 简短理由；
- 确认来源。

不得自动复制完整 grill transcript。普通实施默认只读取 Issue body；只有重新对齐、出现事实冲突、revision 变化或检查确认有效性时才按需读取相关 comments。

Decision Notes 是历史与确认来源，不得单独增加当前义务。材料变化只有在用户确认且规范记录已更新后，才成为当前 Decision Record 的一部分；仓库使用 revision 时再同步递增。

#### FR-11：Issue 生命周期

Issue 生命周期遵循仓库约定和当前授权。以 Decision Issue 作为规范来源时，应在对应结果实施、完成必要验证且关联 PR 或 commit 后关闭。

关闭后的 Issue 是一次决策与交付事件，不是持续与代码同步的活文档：

- 后续内部重构或不改变原用户承诺的修复不更新旧 Issue；
- 后续改变原材料决定时创建新 Issue，并关联 `supersedes`；
- 只有原交付实际未完成、交付证据错误或仍属于同一未完成结果时才重新打开旧 Issue；
- 被替代的旧 Issue 保持关闭并关联替代 Issue。

#### FR-12：历史上下文发现

未来 Agent 不维护单独的 Markdown 决策索引或本地决策数据库。

需要历史上下文时，按以下路径发现：

1. 用户提供的 Issue 或 PR；
2. 相关代码路径、符号或行为的 Git commit；
3. commit 关联的 PR；
4. PR 关联的 Decision Issue；
5. 必要时沿 `supersedes` 链读取最新决定。

没有历史代码路径的新需求可以按功能关键词进行窄范围 Issue 搜索。简单局部任务不强制扫描关闭 Issue。

以材料 Decision Record 作为规范来源时，其落地 PR 应显式关联该 Issue，以保留追溯链路。

#### FR-13：自验证

所有 `DELIVER` 任务都必须进行与最终实现风险相称的自验证。

验证依据包括：

- 当前用户决定或 Decision Record；
- 最终实现 diff；
- 实际暴露的风险；
- 相关回归边界。

早期 Working Strategy、被否决方案、模型猜测和曾考虑的验证方式不得增加最终义务。

#### FR-14：独立检查

`$power-check` 的 Applicability 是运行时唯一触发规则来源。以下情况需要追加独立 `$power-check`：

- 用户明确要求；
- 对安全、隐私、权限、生产持久状态、数据迁移、外部或跨版本兼容、并发正确性或不可逆行为产生材料影响或可信生产风险；
- 准备重要合并、发布或外部交接；
- 实施过程中发生过材料范围或风险偏移；
- Decision Record 明确要求独立证据。

普通、局部、可逆任务在自验证通过后可以完成，不强制独立检查。

仅触碰相关代码、配置、测试、缓存、fixture 或兼容逻辑不足以触发独立检查。高严重度安全、隐私或权限暴露即使 diff 很小仍属于材料风险；向后兼容的可选字段、临时或内部缓存、测试 fixture 及范围狭窄且低风险的兼容修复，在相称自验证充分时不强制独立检查。

需要独立性时使用新鲜、非实施上下文。caller 必须先准备并校验 Check Packet，其中包含模式、决策来源、明确范围外、最终实现身份、自验证证据和外部证据；delta 模式还包含前次身份、结果、findings 及处置。普通缺字段由 caller 补齐；reviewer 仍收到不完整包时返回 `BLOCKED` 并指出 caller 操作。只有缺少 caller 无法提供的用户决定、解释或授权时才返回 `NEEDS_HUMAN`。

独立检查只在计划内实施修改与相称自验证完成、当前 Decision Record 或已验证本地快照可用、最终实现身份稳定后启动。已 commit 候选只有在 index、工作树、全部 untracked 和 submodule 状态前后均为空时才能只用 commit SHA 绑定，reviewer 检查该 commit tree；否则绑定 `HEAD`、`git diff --binary --full-index --no-textconv HEAD --` 原始字节的 SHA-256，以及使用 NUL-safe 枚举得到的逐文件 untracked manifest（相对路径、类型、文件字节或符号链接目标）。前后必须按完整配方重算，不能只比较 `HEAD`。

首次检查完整最终 diff。检查发现问题并完成修复后，优先继续使用仍然独立的同一 reviewer 上下文；不可恢复时可以创建新的独立 reviewer，但 delta packet 必须包含前次身份、结果、findings 和处置并披露上下文替换。delta 检查只覆盖相对已检查身份的变化、受影响决定映射和回归证据；未受影响的 Decision Record 映射、源码检查、验证证据和外部快照必须复用。只有材料范围、决定、决策来源或证据边界变化时才重新执行完整独立检查。

已经提供来源身份与哈希的本地 Decision Record 快照时，不得为重复取证重新联网。不得仅为复制已有支持平台证据而在不兼容平台运行命令。

#### FR-15：power-check 边界

`$power-check` 是独立、只读的实现检查 skill，并明确区分 caller 与 reviewer。Check Packet 是两者之间的唯一接口；caller 决定适用性、绑定实现身份、提供证据、委派并在返回后复核，reviewer 在新鲜非实施上下文中按包执行检查。它只依据：

- 当前确认的用户决定或 Decision Record；
- 明确范围外；
- 最终实现和 diff；
- 自验证及必要外部证据；
- 最终树或等价稳定实现身份。

它不得把 Working Strategy、早期方案、Blueprint、历史测试设想或 comments 中未进入当前 Decision Record 的内容当成合同。

#### FR-16：power-critic 边界

保留显式可选的 `$power-critic`：

- 使用新鲜上下文批量挑战 Decision Record、方案、规格或模型回复；
- 用于发现当前 Agent 与用户共同形成的错误锚定；
- 不自动运行，不是普通交付的门禁；
- 不修改 Decision Record，不实施代码，不检查代码 diff 正确性；
- 任何建议引起的决定变化都必须回到 `$power-gan` 中确认。

#### FR-17：旧流程替换

新核心工作流由 `$power-gan`、`$power-check` 和显式可选的 `$power-critic` 组成。

本次设计不要求兼容或保留以下旧职责划分：

- `power-think`；
- `power-grill`；
- `power-loop`；
- `power-verifier`。

`power-curator`、`power-work-report` 等业务或维护型 skill 不属于本次重设计范围。

#### FR-18：轻量、按比例的 subagent 编排

小任务由主上下文直接完成。需要委派时，通过受管理的具名 profile 按任务形态路由；model 和 reasoning effort 由各 profile 自己持有，spawn 时不重复覆盖：

- 清晰、有界的实现、测试、修复、文档和确定性验证使用 `power_worker`、`gpt-5.6-terra`、`high`；
- 多假设探索、仓库调查、根因分析和跨模块追踪使用行为只读的 `power_explorer`、`gpt-5.6-sol`、`medium`；
- 真正模糊的规划、拆分、跨 agent 结果综合和冲突分析使用行为只读的 `power_planner`、`gpt-5.6-sol`、`xhigh`；
- 完成态实现审查和必须执行的 `$power-check` 使用唯一命名的受管理自定义 `power_reviewer`，避免与宿主内建 `reviewer` 冲突；其 profile 单独拥有 `gpt-5.6-sol`、`high` 和禁止写入、禁止递归委派的 developer instructions。reviewer 的 sandbox 继承宿主，不作为本工作流的通过条件。

模型路由、任务包和 agent 分配是可逆执行策略，不要求用户确认，也不作为 Blueprint 或 Agent Dispatch Plan 持久化。主上下文保留对齐、材料决定、路由、最终仲裁和用户沟通；subagent 的计划、综合、实现或审查结果只能作为主上下文的输入。

任务包使用 `fork_turns: none` 或宿主允许的最小正数历史片段。只并行稳定输入上的只读调查或写入所有权不重叠的任务，并禁止生成的 subagent 继续递归委派。`power_worker` 遇到材料歧义或任务包外工作时返回证据，由 `power_explorer` 或 `power_planner` 处理不确定性后再发出明确实现任务。行为只读的 agent 与未提交工作并行且结果用于检查、合并或交接判断时，主上下文在其返回后复核工作树不变；任何变化都会使旧检查对变化内容失效。

当前自定义 agent 覆盖的验证基线为 Codex CLI 0.145.0 multi-agent V2；0.144.1 不作为支持基线。

宿主无法兑现精确覆盖时，只在仍然足够的情况下使用通用委派或主上下文；精确模型或独立上下文本身是要求时，必须暂停并报告，不能伪造保证。

### 非功能需求

- NFR-1：默认使用简体中文进行用户沟通和持久化工作流记录；精确标识符保持原文。
- NFR-2：简单任务不得因为流程本身强制生成持久化产物或独立 reviewer。
- NFR-3：Deep Grill 每轮必须提出一至三个最高杠杆问题；存在依赖、复杂或高风险分支时只问一个，只有同一决策层的独立问题才可合并为两个或三个。
- NFR-4：不得依赖特定模型名称、推理级别或可选择的自定义 Agent 才能完成基础工作流。
- NFR-5：操作性 skill 只在宿主显式暴露且能够验证的能力上描述轻量编排，不维护双轨模板、Capability Preflight 确认门或 Agent Dispatch Plan，也不把调度策略升级为用户合同。
- NFR-6：不得使用固定文件数量、代码行数、测试数量或固定耗时作为普遍完成标准。
- NFR-7：持久化记录必须允许人和模型理解当前决定，但不得要求普通执行加载完整历史讨论。
- NFR-8：不得为兼容尚未稳定的旧 Issue、Blueprint、Dispatch 或 verifier 产物增加新复杂度。
- NFR-9：对齐对话不得强制使用选项表单、虚假对称或固定反方模板；除宿主要求的一句简短 skill 声明外，不播报模式标签或与当前决定无关的后续审批步骤。

## 已选方案

### 能力与 Skill 的关系

新体系保留三种能力，但不将其机械映射为三个顺序 skill：

| 能力 | 所有者 | 用户入口 |
|---|---|---|
| 对齐与材料决定 | 用户与主 Agent 协作 | `$power-gan` 的 `ALIGN_ONLY` 或 `DELIVER` 前置阶段 |
| 自适应实施与自验证 | 主 Agent | `$power-gan` 的 `DELIVER` |
| 独立实现检查 | 新鲜、非实施上下文 | `$power-check` |

`$power-critic` 是可选的独立方案批评能力，不进入普通主路径。

### 状态模型

```text
用户请求
  -> 推断只讨论还是交付；不明确时只问是否实施
  -> 调查可发现事实
  -> 沿实际决策树解决缺失的材料边界
      -> 只讨论：交付当前决定并停止
      -> 交付：展示精简执行边界
          -> 用户直接要求实现且边界未变化：开始实施
          -> 新材料承诺、先审设计要求或缺少授权：等待确认
          -> 边界内维护可调整的 Working Strategy
          -> 材料偏移：回到对齐
          -> 内部调整：直接继续
          -> 最终候选：完成自验证并稳定 tree/diff
              -> 无独立检查触发：完成
              -> 触发独立检查：首次检查完整最终 diff
                  -> 无发现：完成
                  -> 修复发现：同一 reviewer 只复查 delta 与受影响证据
```

### 权责边界

| 决定类型 | 默认决定者 | 是否需要用户确认 |
|---|---|---|
| 外部结果、范围、材料风险和成本 | 用户，在模型异议和建议基础上 | 是 |
| 长期子系统、所有权边界、共享契约及昂贵逆转的架构选择 | 用户，在主 Agent 建议基础上 | 是 |
| 精简执行边界、硬约束和暂停条件 | 主 Agent 说明，用户可约束或改向 | 直接实施请求已授权其明确范围；新增材料承诺时确认 |
| 文件、局部私有接口、算法、实施顺序、测试方式 | 主 Agent，用户可约束或改向 | 边界内否，除非越界 |
| 安全、权限、不可逆授权是否合法充分 | 用户与适用安全边界 | 必须满足，不能由普通确认绕过 |
| 最终实现是否符合决定 | 自验证；适用时由 `power-check` 独立检查 | 按风险触发 |

### 持久化分层

| 内容 | 默认位置 | 生命周期 |
|---|---|---|
| 需要规范来源的当前材料决定 | Issue body 的 Decision Record | 按仓库约定和授权管理 |
| Issue 创建后的材料变化 | 简短 Decision Note comment | 随 Issue 永久保留 |
| 小型交付的上下文和证据 | PR | 随 PR 保留 |
| 极小修改 | commit | 随 Git 历史保留 |
| 精简执行边界 | 当前会话；其中的材料约束复用 Decision Record | 当前交付期间 |
| 当前实施策略 | 当前会话 | 默认不持久化 |
| 可机器表达的长期约束 | 测试、schema、类型、配置或代码 | 与代码共同演进 |
| Agent 行为约束 | 经确认的就近 `AGENTS.md` | 按项目指令流程维护 |

## 范围外

- 不实现本规格中的 skill 或安装器变更。
- 不编写具体实施 Blueprint、文件修改清单、任务拆分或命令计划。
- 不迁移、转换或兼容已有 Task Contract、Blueprint、Dispatch Plan 或 verifier 结果。
- 不修改 Issue #29 或 PR #30 的现有功能实现和生命周期状态。
- 不自动合并、发布或关闭托管 PR。
- 不改变 Codex 宿主的 skill 发现、上下文继承或 subagent 能力。
- 不训练或修改 GPT 基础模型；反谄媚通过工作流协议约束。
- 不建立项目决策 Markdown 库、全量 Issue 索引、数据库或远程同步服务。
- 不重设计 `power-curator`、`power-work-report` 或其他业务型 skill。

## 验收标准

### AC-1：单一主工作入口

Given 用户调用 `$power-gan`
When 用户明确表示只讨论或需要实施
Then workflow 分别只对齐或继续交付；`ALIGN_ONLY`、`DELIVER`、`FAST`、`DEEP` 只在用户主动使用时作为简写，Agent 不把它们展示成菜单；意图不明确时只追问是否实施。

### AC-2：简单任务快速交付

Given 任务明确、局部、可逆且没有材料风险
When 进入 `DELIVER`
Then 简短说明实施意图和验证方向后直接完成，不额外等待启动授权，也不强制创建 Issue、规格、Blueprint 或独立检查。

### AC-3：Deep Grill 内部切换

Given 当前任务存在多个相互依赖的材料决定
When 需要 Deep Grill
Then Agent 直接从杠杆最高的未决问题开始沿决策树追问；只有访谈会显著扩大预期时间或范围时才先请求同意。

### AC-4：沿材料决策树追问

Given 已进入 Deep Grill
When 仍存在未解决分支
Then Agent 每次回答后更新理解和必要证据，每轮询问一至三个最高杠杆问题并为每个问题给出推荐答案后停下来等待；依赖、复杂或高风险分支只问一个，同层独立问题才可合并；不先倾倒完整设计或提前解决下游分支，只追问属于用户权责的材料决定。

### AC-5：自然推荐与真实异议

Given Agent 需要用户作出材料决定
When 提出问题
Then 从当前证据给出一个推荐并询问杠杆最高的实际边界；用户拒绝或询问替代方案后再逐轮探索其他可信路径，只在存在真实异议时提出反对理由，不强制 A/B/C、虚假对称或固定反方模板，也不让用户选择可逆实施细节。

### AC-6：确认按上下文解释

Given 前一条问题已经清楚复述一个或多个紧密相关的材料边界并询问是否整体接受
When 用户回复“可以”“确认”或其他简短确认
Then Agent 接受该确认；只有回复存在多个合理指向时才追问具体边界。

### AC-7：有界异议

Given Agent 有具体证据认为用户方案过度复杂、矛盾或收益不抵成本
When 用户第一次坚持但没有回应关键异议
Then Agent 再次指出未解决问题；用户明确理解并接受代价后拥有普通产品决定权，适用停止条件仍然有效。

### AC-8：精简 Decision Record

Given 任务需要 Issue 持久化
When 创建或更新 Decision Record
Then 只记录当前结果、边界、材料决定、简短理由、已接受成本风险、停止条件和状态，并仅在仓库采用 revision 时记录 revision；主要未选方案仅在有助于解释非直观边界或避免重复争论时记录，不得为了填充格式而编造，也不记录实施或评审细节。

### AC-9：Decision Notes 而非完整 Transcript

Given Issue 创建后出现材料决定变化或关键授权
When 需要保留历史
Then 使用简短 comment 记录 Decision Note，不自动复制完整 grill 对话；普通执行默认只读取当前 Issue body。

### AC-10：按任务价值选择记录载体

Given 高风险、长周期、跨会话或多人协作的任务需要规范决策来源
When 对齐完成
Then 按仓库约定和授权使用 Issue；普通 PR 级任务可以只使用 PR；极小修改可以只依赖 commit；材料性本身不强制创建 Issue，也不自动生成项目决策 Markdown。

### AC-11：Issue 有结束时间

Given Issue 对应结果已经实施并完成必要验证
When PR 或 commit 已关联
Then 按仓库约定和当前授权关闭 Issue；后续改变原材料决定时优先创建新的 superseding Issue，而不是持续修改旧 Issue。

### AC-12：通过代码历史发现上下文

Given Agent 修改既有公共行为或长期约束
When 需要了解历史决定
Then 通过相关 commit、PR 和关联 Decision Issue 获取上下文，必要时沿 supersedes 链读取最新决定，不默认扫描全部历史 Issue。

### AC-13：直接实施请求即为范围内授权

Given 用户已经直接要求实现，且材料对齐和只读调查没有改变其明确范围
When 即将首次修改源代码
Then Agent 简洁展示完成口径、硬约束、最小可信路径、验证方向和暂停条件后直接实施；只有出现新材料承诺、用户要求先审设计或缺少外部/不可逆授权时才等待确认。边界内文件、局部私有接口、算法、顺序和测试方式可以自主调整。

### AC-14：材料偏移重新对齐

Given 实施暴露新的持久状态、权限、安全、迁移、兼容性、并发、不可逆行为、独立功能或显著成本膨胀
When 当前决定没有覆盖该边界
Then Agent 明确说明执行已经暂停，解释变化并推荐最小可信处理；只有多个方案真正可行时才列出替代路径。普通边界内重新规划直接继续，材料变化确认后按仓库约定更新规范记录。

### AC-15：验证依据来自最终实现

Given 已形成最终候选
When 选择验证方式
Then 根据用户决定、最终 diff 和实际风险进行自验证，早期 Working Strategy、模型猜测和被否决方案不增加额外合同。

### AC-16：独立检查按风险追加

Given 用户要求独立验证，或任务涉及材料风险、重要交付或显著偏移
When 自验证完成
Then 在计划内实施修改与自验证完成后，caller 构造并校验 Check Packet，按完整配方绑定最终实现身份，再委派给新鲜、非实施的 `power_reviewer`。commit SHA 模式要求前后工作树完全干净；非 commit 模式绑定 binary full-index diff 和逐文件 untracked manifest。reviewer 的 developer instructions 禁止写入和递归委派，不要求宿主强制降级 sandbox。仅触碰风险类别的普通可逆任务不强制独立检查。修复后优先恢复同一 reviewer；不可恢复时允许新 reviewer 使用含前次结果和处置的 delta packet，只复查 delta 与受影响证据；材料范围、决定、来源或证据边界变化时才重新完整检查。

### AC-17：不能伪造独立性

Given 宿主无法提供新鲜、非实施上下文
When 独立检查是必需的
Then 当前实施 Agent 不得自称完成独立验证，而应返回 `CHECK_REQUIRED` 和明确的检查入口。

### AC-18：power-check 只检查用户承诺

Given `$power-check` 获得最终实现和证据
When 执行只读验证
Then 只检查当前 Decision Record 或用户决定、范围外、最终 diff 和明显回归，不把 Working Strategy 或历史提案当成合同。

### AC-19：power-critic 显式可选

Given 用户需要新鲜上下文挑战当前方案或双方共同前提
When 显式调用 `$power-critic`
Then 它只提供批量批评，不修改决定、不实施代码，也不成为普通交付的强制门禁。

### AC-20：Issue #29 回放

Given 使用新流程处理 Issue #29 的原始三项需求
When 讨论日报洞察和持久指令写入
Then Agent 主动指出它们属于不同价值和风险边界，提供拆分与更小方案；未经分别确认，不自行加入事务、并发、审计、回滚或灾难恢复保证。

### AC-21：结果契约主结构

Given Codex 加载 `$power-gan` 的操作性指令
When 执行需求对齐、交付或验证
Then `Core Contract`、`Ownership And The Materiality Test`、`Decision Ledger`、`Alignment: The Grill Loop`、`Delivery`、`Validation And Independent Check`、`Persistence` 和 `Orchestration` 构成主结构，Grill Me 仍是材料对齐的核心行为，原有授权、持久化和独立检查边界保持不变。

### AC-22：模型路由轻量且可验证

Given 当前 Codex 支持受管理的自定义 agent profile
When `$power-gan` 将边界清晰的实现、复杂探索、模糊规划或完成态审查交给 subagent
Then 分别使用 Terra/high `power_worker`、Sol/medium `power_explorer`、Sol/xhigh `power_planner` 或 Sol/high `power_reviewer`；每个 profile 自己持有模型和 effort，explorer、planner 和 reviewer 通过自然语言约束保持行为只读，主上下文保留最终仲裁，任务包不持久化，宿主不能兑现 profile 配置时不声明精确保证。

### AC-23：Decision Ledger 不丢失材料决定

Given Grill 已跨越多个回合且用户只回答了部分问题或明确委托了部分边界
When 进入下一轮、结束对齐或生成 Decision Record
Then 未回答推荐仍位于“待定”，明确委托位于“已委托”，可逆工作默认值与材料决定分开，Decision Record 覆盖全部“已确认”和“已委托”的材料项。

## 已解决问题

- 谁决定实施细节？ -> 模型对可逆内部实现拥有默认执行权；用户保留知情、约束、改向和停止权，但不逐项审批边界内调整。
- 内部架构和接口是否都由模型决定？ -> 否；建立长期边界、共享契约或昂贵逆转约束的内部选择也属于材料决定，局部私有接口仍由模型自主处理。
- 用户如何在不频繁打断的情况下掌控实施？ -> 直接实施请求授权其明确范围；Agent 在首次写入前说明精简边界，只有新材料承诺、先审设计要求或缺少授权时才再次阻塞。
- 是否让 Blueprint 和测试矩阵也经过更多 grill？ -> 否；它们不应成为用户合同。
- 模型与用户冲突时怎么办？ -> 使用有界异议；知情后由用户决定普通产品取舍。
- 是否兼容旧流程？ -> 完全不考虑旧格式和阶段兼容。
- 是否每个材料决定都创建 Issue？ -> 否；只有仓库约定和协调需要规范来源时使用 Issue，其他任务使用 PR 或 commit。
- 是否建立仓库决策 Markdown？ -> 否；过去实践证明会膨胀并与代码漂移。
- Issue 是否长期随代码维护？ -> 否；交付后关闭，材料改变时创建 superseding Issue。
- 是否保存完整 grill 对话？ -> 否；只保存当前 Decision Record 和少量 Decision Notes。
- 是否每项材料决定都记录被否决方案？ -> 否；只在有助于解释边界或避免重复争论时，可选记录最接近但未选择的方案。
- Comments 给谁看？ -> 人和模型都可按需读取，但普通实施不加载全部历史。
- Deep Grill 如何保持自然？ -> 先调查事实，只追缺失边界；每轮围绕同一决策层提出一至三个最高杠杆问题，依赖、复杂或高风险分支只问一个，并为每个问题给出推荐答案。
- 对齐与交付是否拆成两个 skill？ -> 否；共享协议和上下文使其更适合作为一个主工作 skill 的不同目标。
- 独立检查是否每次运行？ -> 否；所有任务自验证，独立检查按风险追加。
- `power-critic` 是否保留？ -> 保留为显式、非门禁的新鲜上下文批评能力。
- 主工作 skill 名称是什么？ -> `$power-gan`。

## 前提

- 托管 Issue 和 PR 平台及网络默认可用。
- Agent 可以读取仓库、Git 历史、相关 Issue、PR 和 comments。
- 材料 Issue 的落地 PR 或 commit 能够保存可追溯关联。
- 用户能够对材料决定给出可识别的选择或明确授权。
- 代码、测试、schema、类型和配置仍是当前实现事实的主要来源。
- `$power-gan` 中的 `gan` 是用户确认的名称；英文语境可能将其理解为 GAN，但本规格不因此更名。
