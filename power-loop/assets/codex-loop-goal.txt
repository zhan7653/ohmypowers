/goal Execute the confirmed Task Contract at <contract-source> using its confirmed Execution Blueprint and Agent Dispatch Plan. For verification, treat the complete canonical Issue/local body together with this final Goal Prompt as the contract; do not copy, reinterpret, criticize, or revise either source.

Confirmed planning references:
- Contract source: <contract-source>
- Execution Blueprint section: <section heading or anchor>
- Agent Dispatch Plan section: <section heading or anchor>
- Planned source baseline: <source-branch>@<full-commit-sha>

Preflight:
1. Read the complete persisted Issue/local body, this final Goal Prompt, Execution Blueprint, and Agent Dispatch Plan.
2. Require both execution sections to say `Planning status: confirmed`.
3. Check the current repository against the recorded source branch and commit. If the commit differs, inspect whether changes materially affect planned paths, interfaces, dependencies, validation commands, or assumptions. Stop for a new power-loop pass or confirmed plan revision when drift is material.
4. Confirm every contract-prescribed reviewer and every required custom agent named by the Dispatch Plan is discoverable with the specified settings. Do not silently inherit or substitute a model, provider, agent, or procedure; pause and report missing configuration unless the contract or confirmed plan names an approved alternative.
5. Confirm the Task Contract still has precedence over both execution sections. Stop on any conflict.

Main-agent role:
- Act as the orchestrator for interfaces, dependency coordination, conflict resolution, dispatch, waiting, steering, escalation decisions, validation coordination, review coordination, and result consolidation.
- Do not normally edit implementation files. Delegate implementation changes to the exact worker profiles and Task IDs in the confirmed Dispatch Plan.
- If delegation is unavailable, pause unless the confirmed Dispatch Plan explicitly authorizes a narrow main-agent exception with exact paths and rationale.
- Do not expand scope, alter public contracts, or revise confirmed execution sections during the run.

Work isolation and ownership:
- Create or enter the dedicated implementation branch/worktree specified by the Execution Blueprint, based on its recorded source branch.
- Do not perform normal implementation writes directly on the shared source/integration branch.
- Do not create one worktree per subagent.
- Preserve unrelated user changes.
- Start write-capable workers in parallel only when their allowed write paths and interface responsibilities do not overlap.
- Serialize overlapping files, unstable shared interfaces, and unresolved dependencies.
- Keep explicit ownership throughout the run; stop and resolve ambiguity before additional writes.

Dispatch:
- Execute the confirmed task graph and dependency waves.
- Preserve meaningful parallelism for independent deliverables; do not reduce agent count merely as a cost metric.
- Give every agent its Task ID, objective, relevant contract and Blueprint excerpts, allowed paths, dependencies, deliverable, validation responsibility, and stop conditions.
- Wait for required task results, steer only within the confirmed contract, and consolidate artifacts without redoing completed worker exploration.

Model escalation:
- Allow at most one model escalation per implementation task.
- Escalate only when failure evidence shows that the initial model assignment underestimated capability or reasoning needs.
- Do not escalate for permission, environment, dependency, unavailable validation, interface-conflict, or other non-capability failures.
- Reclassify directly to the lowest sufficient target allowed by the confirmed task entry; do not step through every tier.
- Use Terra Medium or Terra High when sufficient. Sol Medium is the ceiling, not the default escalation target.
- Never exceed `power_sol_escalation` on `gpt-5.6-sol` Medium for implementation.
- Give the replacement worker the prior worker's useful findings, failure evidence, artifacts, and current state.
- If Sol Medium cannot complete the task, stop and report the blocker.

Validation loop:
- Run the exact validation commands and manual checks from the confirmed Execution Blueprint.
- Run targeted validation after meaningful changes, then the full required validation before review.
- Diagnose failures before retrying and do not hide failing or unreliable validation.
- Capture the stable implementation snapshot before accepting validation or review evidence: repository/ref, commit, diff or tree digest, dirty/generated boundary, and capture time.
- Independently replay contract-required validation when it is safe against that snapshot. Record the exact command, safety class, result, relevant evidence, and snapshot identity. Writable artifacts are allowed only in a disclosed isolated environment that does not mutate the canonical snapshot or hosted state; otherwise disclose why replay did not run.
- Pause when validation cannot prove the acceptance criteria or when forbidden/high-risk work becomes necessary.

Budget:
- Max implementation iterations: 5.
- Same-failure retry limit: 3.
- Stop after 3 consecutive no-progress iterations.
- Pause on scope expansion, material plan drift, missing validation, forbidden paths, unapproved high-risk operations, or missing required agents.

Verifier gate:
- After the final diff, validation output, acceptance-criteria evidence, and draft PR/MR evidence package are stable, build the review plan against the captured snapshot. The evidence package may remain local until review finishes.
- If the contract names exact reviewers, agents, models, providers, or procedures, run and verify them exactly. Do not silently substitute unavailable requirements.
- Otherwise, select the minimum sufficient independent, read-only capabilities from the contractual obligations, final diff, affected interfaces/data, validation requirements, and material security, compatibility, migration, data, permission, concurrency, and domain risks. Do not impose a fixed review count, profile, model, provider, or specialization.
- Require at least one reviewer independent from implementation to perform contract-conformance review before `PASS` or `PASS_WITH_NOTES`. Add code, test, security, compatibility, migration, data, or domain review only when the contract or identified risk justifies it.
- For every reviewer, record identity/source, implementation independence, capability, scope, read-only boundary, evidence inspected, result, and snapshot identity. Give the contract-conformance reviewer the complete canonical Issue/local body and final Goal Prompt, clause/AC evidence, stable snapshot, validation replay, changed-path/scope manifest, PR/MR evidence, risks, assumptions, and non-goals; tailor other packets to their capabilities.
- Run independent selected reviews in parallel over the same snapshot when possible. Contract-prescribed reviews do not consume or substitute for one another.
- Route fixable `BLOCKED` findings back to the owning implementation task within the remaining budget. A repair creates a new snapshot, invalidates affected validation and review evidence, and requires the relevant replay and reviews again.
- Use `NEEDS_HUMAN` for scope changes, contract conflicts, required human interpretation or authorization, unavailable contract-prescribed capabilities requiring approval, or repeated repair failure beyond budget.

PR/MR evidence:
- After all planned reviews finish, create or update a draft PR/MR only; do not merge or push directly to a protected branch.
- Link <contract-source> and reference its confirmed Execution Blueprint and Agent Dispatch Plan.
- Include summary, rationale, changed files, clause/acceptance-criteria evidence, stable snapshot, validation replay, review plan and reviewer provenance, verifier result, the final Dispatch Summary, risks, assumptions, out-of-scope items, issue curation handoff, and loop decision.
- Do not mutate issue bodies, labels, comments, or closure state without separate explicit confirmation of the exact curation mutation.

Dispatch Summary:
- Report planned and actual task counts.
- For every task, report initial model and final model. For every implementation task, also report escalation status and reason.
- Report dependency wave and parallel/sequential execution.
- Report ownership conflicts and resolutions.
- Report incomplete tasks and pause reasons.
- Calculate Initial Assignment Accuracy as implementation tasks completed without escalation divided by completed or attempted implementation tasks that received an initial assignment.

Loop decision:
- `pr-ready`: a draft PR/MR exists, required validation passes, all contract-prescribed reviews or the selected minimum sufficient capability plan are complete, an implementation-independent contract-conformance review exists, and the verifier result is PASS or PASS_WITH_NOTES.
- `blocked`: a technical or capability blocker prevents progress within the confirmed contract and budget.
- `needs-human`: a human decision or approval is required.
- `follow-up-needed`: the current contract is complete, but new work belongs in a separate issue.
- `done`: use only after human confirmation, not immediately after agent implementation.

Final response:
- State the loop decision.
- Summarize completed work and validation evidence.
- Include the stable snapshot, validation replay, reviewer provenance, verifier result, Dispatch Summary, and remaining risks or human decisions.
- Do not merge.
